## 3. Business and system context

- **The clearing process (outside this app):** every night, an automated job reads the day's cheque images and records:
  - an AI model extracts the cheque fields, and a second document reader is optional;
  - a signature model compares the signature with the member's specimen;
  - a rules engine decides **pay / return / review** for each cheque.

  It writes the results to **Azure SQL** (decisions with model, prompt and rules versions; policy; feedback; audit) and to **Cosmos DB** (raw model outputs and evidence packages as JSON).
- **This app:** reviewers decide the cheques marked **review** before the daily clearing cut-off. Policy administrators manage the rules' thresholds and reason codes. ML engineers look at quality and use reviewer feedback to retrain models.
  - Sign-in is through **Microsoft Entra ID** with roles.
  - Personas: **CAPS reviewer**, **policy administrator**, **ML engineer**.
- **Azure Databricks:** the data platform holds the curated cheque data, clearing history, the image manifest and model metrics as Delta tables in Unity Catalog. It also holds the **labelled data** used to retrain the models. This app reads context and metrics from it and writes reviewer corrections and labels to it.
- **Writeback to core banking (outside this app):** a separate service reads **final decisions** from Azure SQL and updates the core banking system (T24). It records a writeback status. This app only **reads** that status; it never calls T24.
- **Governance expectations:**
  - **Human oversight:** reviewers make the final call on flagged cheques.
  - **Keyless access:** managed identities, no keys or passwords.
  - **Network:** private networking.
  - **Logging:** no cheque content in logs.
  - **Audit:** a full audit trail per cheque, with a defined retention period.
- Keep the code container-friendly, so it could also run on Azure Container Apps later if needed.

## 6. Data: what the app reads and writes

**Azure SQL is the system of record for decisions.** Cosmos DB holds evidence documents, and Databricks holds history, metrics and retraining labels. Propose exact schemas only if I said we do not have them. The expected shape is:

**Azure SQL (read/write)**
- `Decision`:
  - cheque ID, business date, run ID;
  - model, prompt and rules versions;
  - automatic outcome, confidence and signature score;
  - status: `PendingReview`, `InReview`, `Decided`, `SentToWriteback`, `WritebackDone`, `WritebackFailed`;
  - final outcome, reason code, reviewer and timestamps;
  - a `rowversion` for optimistic concurrency.

  **One decision per cheque per business date.**
- `ReviewAssignment` (or lock columns): who claimed the cheque and when the claim expires (for example, 15 minutes).
- `ReviewerFeedback`: corrected fields (field name, model value, corrected value), signature verdict, free-text comment, and a "bad read" flag.
- `PolicyVersion` and `PolicyRule`: versioned, with exactly one active version at a time. Activation is an explicit, audited action, and old versions are immutable.
- `AuditEvent`: **append-only** (who, what, when, cheque or policy ID, before and after values as JSON). The app never updates or deletes these rows.
- `WritebackStatus`: **read-only** for this app (written by the separate writeback service).
- `Outbox`: pending writes to Cosmos and Databricks (see "How writes happen").

**Azure Databricks (read/write, Unity Catalog)**
- **Read** from `{{CATALOG}}.{{READ_SCHEMA}}`:
  - clearing history for a member account or cheque, shown as context on the cheque detail page;
  - the curated cheque record and image manifest, when they are not in the Cosmos evidence package;
  - daily model and quality metrics for the Insights screen.

  These reads are **not** on the queue's critical path. Cache results briefly and set a per-request timeout. If Databricks is slow or down, the page still loads and shows "history unavailable".
- **Write** to `{{CATALOG}}.{{WRITE_SCHEMA}}`:
  - Reviewer field corrections, signature verdicts and "bad read" flags go to the **labelled data** table(s) used for retraining.
  - Each row carries:
    - cheque ID and business date;
    - model, prompt and rules versions;
    - reviewer object ID (pseudonymised if `{{CONFIRM}}`);
    - the corrected values;
    - a timestamp.
  - Use **`MERGE INTO`** keyed by (cheque ID, business date, field, feedback version), so retries never create duplicates.
  - Never update or delete model outputs or tables the app does not own.

**Cosmos DB**
- **Read:** evidence packages and raw model outputs, by cheque ID. Use **point reads** (ID plus partition key) wherever possible, and avoid cross-partition queries on hot paths.
- **Write:** `{{CONFIRM: does the app write to Cosmos (e.g. reviewer annotations on the evidence package), or only read?}}`. If it writes, use idempotent upserts with ETag concurrency, and never overwrite model outputs.

**How writes happen (consistency across the three stores)**
- There are no distributed transactions. **SQL is authoritative:** the reviewer's save commits the decision, the feedback and an **outbox** row in a single SQL transaction.
- A background `IHostedService` drains the outbox in small batches to Databricks (`MERGE`) and to Cosmos (if it writes there). Writes are retried with back-off, and failures go to a dead-letter state. Retries must tolerate a SQL warehouse cold start.
- Never call Databricks inside the reviewer's save request. A Databricks or Cosmos failure must never block or corrupt the SQL decision.
- Show the sync status for each cheque (`Pending`, `Synced`, `Failed`) to ML engineers.
- Run a daily reconciliation that compares SQL feedback counts with Databricks row counts per business date, and alert on any mismatch.

**Cheque images**
- If the evidence package has an image URI, stream the image through the app's backend using the managed identity, which has read-only access to that container.
- Never send storage URLs or SAS tokens to the browser.
- Show the signature specimen next to the cheque signature when it is available.

## 7. Functional requirements

1. **Review queue** (the default page for reviewers): flagged cheques for a business date, with filters (status, reason, amount range, confidence, branch) and sorting. Show the time left before the **clearing cut-off** `{{CUTOFF_TIME, time zone}}`. Use server-side paging.
2. **Claim and lock:** opening a cheque claims it, so two reviewers cannot decide the same cheque. Claims expire, and `{{ROLE}}` can release or override them.
3. **Cheque detail:** shows
   - the cheque image;
   - extracted fields with per-field confidence, with low-confidence fields highlighted;
   - the signature score next to the specimen;
   - the rule that applied and why, and the automatic outcome;
   - the model, prompt and rules versions.
4. **Decide:**
   - Pay or return, with a mandatory reason code, an optional comment and field corrections.
   - Save with optimistic concurrency, so a stale `rowversion` gives a clear "someone else changed this" message.
   - A decided cheque is read-only. `{{ROLE}}` can reopen it through an audited action, but only before writeback.
5. **Writeback visibility:** show the writeback status and errors per cheque, plus a daily summary. The app never calls T24.
6. **Policy configuration (UI and API):** list versions, compare two versions, create a draft, validate it (schema and range checks), activate it, and roll back by activating an older version. Everything is audited.
7. **Policy API** (`/api/v1/policies`):
   - Endpoints: GET active, GET by version, POST draft, POST activate.
   - Protect it with Entra, using app roles for both user and application callers, and document it in OpenAPI.
   - `{{CONFIRM: who calls this API besides the UI — e.g. the nightly rules engine?}}`
8. **Audit view:** search the audit trail by cheque ID, user or date (read-only).
9. **Insights (ML engineer):**
   - daily counts (auto-decided vs reviewed, overrides, misreads) and model metrics from Databricks;
   - Databricks sync status, with a "retry failed" action;
   - download of feedback and labels for a date range, using the Statement Execution API's `EXTERNAL_LINKS` for large result sets, streamed through the backend.
10. **Accessibility and usability:** see section 8. It is a requirement, not a nice-to-have.

## 9. Engineering best practices

**Code quality**
- Turn on nullable reference types, and treat warnings as errors in CI.
- Use the .NET analyzers with an `.editorconfig`, Central Package Management (`Directory.Packages.props`) and deterministic builds.
- Keep layers clean:
  - Domain has no Azure dependencies;
  - Application holds the use cases and authorization policies;
  - Infrastructure holds the Azure clients.
- Keep methods small and names clear. Write ADRs for significant decisions.
- Use `async` and `CancellationToken` all the way down. Never use `.Result` or `.Wait()`.
- Use the options pattern with **validation on start-up**, so a missing setting fails at deploy time, not in the middle of the night.

**API design**
- URL versioning (`/api/v1`), with the OpenAPI document checked in CI.
- Errors returned as **ProblemDetails (RFC 9457)**; input validation with FluentValidation.
- **ETags / `If-Match`** for updates, **idempotency keys** on POST, and cursor or keyset paging.
- The ASP.NET Core rate limiter on the policy API.

**Blazor Server on App Service (important for scale-out)**
- Design for two or more instances from day one, even though DEV can run on one.
  - Use **Azure SignalR Service** (Default mode) or ARR affinity, so user connections survive. Recommend one and explain why.
  - Persist **ASP.NET Core Data Protection** keys to Blob Storage, protected by Key Vault, so sign-in cookies and antiforgery tokens work across instances and slot swaps.
- Handle reconnects gracefully with a branded reconnect screen, and keep per-user server memory small.

**Performance**
- EF Core: use `AsNoTracking` for reads, projections (`Select`) instead of whole entities, and compiled queries on the hot path. Index for the queue's filters.
- Use Cosmos point reads.
- Use response compression, and serve fingerprinted, cached static assets (`MapStaticAssets`).
- Budgets:
  - queue first paint under 1.5 s and cheque detail under 2 s on the corporate network;
  - a Lighthouse performance score of at least 90 on the app shell.

**Security** (in addition to section 10)
- Follow **OWASP ASVS Level 2** and the OWASP Top 10.
- Set security headers: CSP with nonces, `X-Content-Type-Options`, `Referrer-Policy` and `Permissions-Policy`.
- Run dependency vulnerability scanning, secret scanning and SAST (CodeQL or Azure DevOps Advanced Security) in the pipeline. The build fails on high or critical findings.
- Pin packages, update them regularly, and produce an SBOM for each build.

**Operations on App Service**
- Turn on **Always On**, and set the **health check path** to `/health/ready`.
- Use a **staging deployment slot** with warm-up (`applicationInitialization`) before swapping.
- Use **feature flags** (Azure App Configuration) to switch new screens on gradually and to turn off Databricks reads quickly if needed.
- Write the infrastructure so zone redundancy, multiple instances and autoscale can be switched on per environment through parameters. They can stay off in DEV.

**Testing**
- A test pyramid:
  - fast unit tests, with 80 % or more coverage of domain and application code;
  - integration tests for SQL, Cosmos and Databricks;
  - bUnit component tests;
  - Playwright end-to-end tests, including axe accessibility checks.
- API contract tests against the OpenAPI document.
- A load-test script (Azure Load Testing) at 2× the expected peak, ready to run before go-live.

**Collaboration**
- Small PRs with a PR template (what, why, screenshots for UI changes, tests). Branch policies require one reviewer and a green build.
- Conventional Commits, with a changelog generated for each release.
